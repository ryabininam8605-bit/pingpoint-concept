# Ping Point
Сайт комнаты настольного тенниса в Брянске. Рабочий вариант — `1-neon`; остальные варианты не считать активными без проверки задачи. Python 3.11+. Поведение определяется кодом; `README.md` — инструкция запуска и пользовательские ограничения. Схема потоков и границ модулей — [`docs/architecture.md`](docs/architecture.md).

## Перед изменением
- Сначала проследить вызывающий UI → адаптер → HTTP route → сервис/Store; не переносить ответственность между уровнями без причины.
- Брони и новые аккаунты серверные. Старые community-профили, объявления и их модерация остаются в браузере; ни локальный флаг, ни номер/ID брони сами по себе не дают серверных прав.
- SQLite хранит одну JSON state-строку и таблицу серверных сессий. Все конкурентные изменения выполнять через `Store.transaction`; внешние HTTP-вызовы не делать под write-lock.
- `Store.defaults` должен сохранять совместимость уже созданных баз; `Store.expire` меняет истёкшие pending-брони при транзакциях, поэтому миграции проверять на старой базе.
- Учитывать, что один HTTP request может обрабатываться параллельно другим: сначала проверить владельца/состояние, затем атомарно повторить критические проверки в транзакции.
- Рабочие часы, цена, пересечение слотов и допустимая скидка остаются серверными правилами даже при preview в браузере.
- Публичное представление брони — `booking_view`; расширение его полей может раскрыть личные данные или секрет доступа. QR/token выдаются только отдельным access endpoint владельцу/админу.
- Общая availability-сетка показывает слот/статус/тариф, не имя, телефон или коды; не расширять её приватными DTO.
- Сервер возвращает JSON-ошибки `{error:{code,message}}`; мутации UI идут POST с `X-PP-CSRF`. Webhook и проверка устройства проходят отдельными внешними маршрутами.
- Браузерные аккаунт-сессии и гостевые cookie разные способы владения; при смене auth ротация cookie/CSRF влияет на последующие запросы и кеш сессии UI.
- Телефон в account пока не подтверждён, восстановления по SMS нет; не обещать пользователю такой путь.
- Согласие регистрации сверяется по актуальным id/version/hash документов; на `DOCS_CHANGED` UI должен запросить новое подтверждение.
- Не считать `docsOk:false` отзывом доступа к уже оплаченной брони/QR. Серверный аккаунт не получает локальное автоматическое окно продления согласий; renewal пока неподдержан.
- Оплата требует сконфигурированной ЮKassa и проверенного server-side ответа. `--demo-payments` — только локальная имитация; test/demo не выдают проход. Generic СКУД-коннектор не доказывает совместимость с устройством.
- При `payment_review` деньги подтверждены, но доступ остаётся закрытым до решения по занятости/возврату; не сводить этот статус к обычному `paid`.
- Refund `pending` не равен подтверждённому возврату; в статистике учитывать подтверждённые события, а не только попытку.
- Лимитер аккаунтов работает в памяти процесса. Не описывать его или хранение audit как устойчивую распределённую защиту/политику retention.

## Команды
Из корня проекта. README-запуск: `python server.py --port 8767`. Чтобы поставить dev-зависимости в отдельное Windows venv и выполнить полный check:
```powershell
python -m venv .venv
$env:PATH = (Resolve-Path .venv\Scripts).Path + [IO.Path]::PathSeparator + $env:PATH
python -m pip install -r requirements-dev.txt
node tests/check.mjs
```
Runtime-only install: `python -m pip install -r requirements.txt`. Для изолированной базы добавлять `--database <путь>`. `.env.example` не загружается автоматически; конфигурация читается из process environment. Секреты не выводить и не сохранять.
- Проверенные установки `requirements-dev.txt` и runtime `requirements.txt` завершились успешно; dev-набор содержит 14 закреплённых зависимостей.
- Полная G4 проверка: `node tests/check.mjs` — 10 syntax, 36 Node, 38 Python тестов прошли; 0 ошибок. Команда harness использует `python` из `PATH`, поэтому выбранный venv `Scripts` должен быть первым.
- Отдельно проверено: `python -m unittest discover -s tests -p test_access.py` — 6 тестов прошли (`Ran 6 tests`, `OK`).
## Что легко сломать
- Windows: перед рестартом после изменения схемы остановить старый сервер на порту; прежний процесс может ещё отвечать ошибкой. Проверять `/api/session`, а не только HTML.
- `.data/bookings.sqlite3` — база по умолчанию; QA запускать с отдельным `--database`. Остановка сервера перед копированием/резервом SQLite. `localhost` и `127.0.0.1` разделяют cookie; разные порты на одном hostname — нет.
- Страницы и скрипты раздаются из `/1-neon/`, изображения разрешённых типов — также из `/img/` (там логотип и фото). Не закрывать `/img/` при изменении static allowlist; служебные файлы и выход за эти каталоги закрыты. `python -m http.server` не заменяет API-сервер.
- Если браузер запущен на `127.0.0.1`, для QA использовать `localhost`. Синтетический loopback QA/mock не подтверждает реальные списания, возвраты или физический проход.
- `PP_ADMIN_LOGIN` и `PP_ADMIN_PASSWORD` задаёт владелец в окружении процесса; без обеих переменных серверная админка закрыта. Названия остальных env-групп и назначение см. в `.env.example`, значения не читать/не копировать в память.
- В `community.js` остаётся локальная логика профилей и объявлений; `shared-account.js` связывает её UI с серверной auth, `shared-booking.js` — общий booking/admin адаптер. Серверные данные не импортируют старые локальные брони/профили.
- UI сообщества может использовать локальный профиль для карточки, но не выводит из него серверный `userId` или право открыть чужую бронь.
- Порядок scripts: игрок — `community.js` → `shared-booking.js` → `shared-account.js` → `booking.js`/inline по странице; админ — `community.js` → `shared-booking.js` → `admin-insights.js` → inline. После правки скрипта обновлять cache version на использующих его страницах.
- Сохранять совместимость `BookingAPI`, `AdminAPI`, `AccountAPI`, `pp:change` и `pp:session`. Дождаться `BookingAPI.ready`; пустой синхронный cache при загрузке/ошибке не означает свободный интервал, смотреть `availabilityState`.
- При одинаковом ответе availability повторный fetch не должен порождать бесконечный `pp:change`/перерисовочный цикл.
- После login/logout/password/passkey обновлять authoritative session snapshot и CSRF; локальная карточка профиля без серверного снимка недостаточна.
- Community-документы/модерация остаются локальными даже для вошедшего account; не считать их server consent или server audit.
- Перенос существующей брони сохраняет её `promoTerms`. Админскую ручную цену сначала получать через `quoteManualBooking`, затем передавать `expectedAmount`; сервер может вернуть 409 `QUOTE_CHANGED`. Закрытое окно загрузки не должно продолжать мутацию.
- `server.py` сначала проверяет host allowlist; при настройке публичного адреса `PP_PUBLIC_ORIGIN` требуется HTTPS origin без path. Cookie становятся secure при заданном origin.
- Время слота считается в Москве (UTC+3); QR действует с включённого начала до исключённого конца интервала.
- Авторизация admin хранится в серверной сессии. Успех локального `localStorage`-флага не заменяет вход `/api/admin/login`.
- Интеграции в `/api/session` — readiness/configuration, а не доказательство реальной операции. Серверная админка показывает отдельные account/payment/access capability.
- `gross` в analytics — подтверждённые поступления до комиссии; live и test разделяются, возвраты считаются по успешным событиям.
- `/api/admin/access/simulate` даёт только аудируемый результат `simulation:true`; физическую команду двери не добавлять.
- Неподключённые платёжный провайдер и СКУД должны оставаться явно not ready; generic online verifier — не vendor adapter. Backlog и состояние Autopilot смотреть по указателю `.autopilot/PROGRESS.md`, не пересказывать его здесь.
