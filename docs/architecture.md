# Архитектура Ping Point

Этот документ фиксирует текущие границы и потоки, чтобы изменения попадали в правильный слой. Источник истины для деталей остаётся в коде.

## Потоки

### Страница и API

`server.py` создаёт `ThreadingHTTPServer`, раздаёт допустимые статические файлы внутри `1-neon/` и изображения разрешённых типов из `img/`, маршрутизирует `/api/*` через `Handler.dispatch`. При первом запросе сервер создаёт cookie-сессию; API-ответы включают нужные JSON DTO, ошибки нормализуются в `{error:{code,message}}`. POST браузера проверяет Origin и `X-PP-CSRF`; webhook и запрос устройства идут по своим правилам авторизации.

`GET /api/session` — начальный снимок для UI: серверные настройки, capability flags, пользователь из аккаунт-сессии, CSRF и режим оплаты. Клиентские localStorage-флаги не превращаются в серверную сессию. Для обычных booking/account/admin операций права повторно проверяются на сервере.

### Брони и хранение

`server.py` проверяет дату, рабочие интервалы, занятость, скидку и доступ владельца. `Store.transaction` открывает `BEGIN IMMEDIATE`, читает JSON state, применяет defaults/истечение удержаний, выполняет действие и сохраняет целый state. Сессии хранятся отдельными SQL-строками. Новые ключи state добавляются через defaults, чтобы существующая база дополнялась без сброса.

Бронь создаётся с серверной проверкой свободного времени и 15-минутным удержанием; отмена/истечение меняют общее состояние. `booking_view` — внешний безопасный DTO: не добавлять в обычные списки телефон/секрет QR или внутренние операции. Админские ручные цены проходят серверный quote/`expectedAmount`; расхождение должно оставаться конфликтом, а не тихой коррекцией.

### Аккаунт

`identity.py` отвечает за пароль/scrypt, согласия с хешами документов, профиль, passkey ceremonies и лимитер попыток. `server.py` связывает это с cookie session и ротацией CSRF. User ownership устанавливается по session `userId`; гостевая бронь остаётся привязанной к случайной cookie. Passkey challenge одноразовый и связан с назначением и сессией. Лимитер — процессный, не общий между несколькими worker-процессами.

`1-neon/shared-account.js` добавляет серверную auth к локальному community UI. Профиль community может быть дополнен серверным account, но локальный профиль не является доказательством владения account или брони. Устаревшие локальные согласия не авторизуют серверные изменения.

### Оплата и доступ

`payments.py` формирует устойчивую операцию и idempotency key внутри SQLite-транзакции, затем вызывает провайдера вне транзакции. Ответ и webhook сверяются с локальным payment/booking, суммой, валютой, режимом и metadata; неопределённый исход не должен порождать новую попытку списания. `analytics.py` — чистая агрегация событий state: live/test раздельны, денежная арифметика начинается в копейках, даты — московские.

`access.py` выдаёт непрозрачный токен только после подтверждённой реальной оплаты. Владелец читает QR отдельным access endpoint; проверка устройства сопоставляет hash токена, оплату, статус и строгий интервал `validFrom <= now < validTo`. Перенос/отмена/возврат должны отзывать старый grant. Simulator только пишет решение с `simulation:true`; команды открытия двери нет.

## Границы и владение

- `server.py` владеет HTTP, сессиями/CSRF, маршрутами, booking правилами и Store. Он связывает модули, но провайдерные детали оплаты принадлежат `payments.py`, вычисление решения/QR — `access.py`.
- `identity.py`, `analytics.py`, `payments.py`, `access.py` работают с переданными state/service collaborators; не добавлять в эти модули UI-код или прямое управление HTTP-страницами.
- `community.js` держит локальные CommunityAPI, согласия, объявления и общие UI-компоненты. `shared-booking.js` адаптирует API бронирования/админки и кеш доступности к серверу. `shared-account.js` соединяет серверную auth с community. `booking.js` содержит UI потока бронирования.
- `admin.html` содержит формы и навигацию; `admin-insights.js` обслуживает отдельные административные графики/пользователей/платёжные представления. Сохранять разграничение local community data и server account/payment data.
- `1-neon/index.html` и `cabinet.html`: `community.js` → `shared-booking.js` → `shared-account.js` → страничный inline/`booking.js`; `admin.html`: `community.js` → `shared-booking.js` → `admin-insights.js` → inline. Изменение общей функции требует проверки всех её страниц и обновления query-version скрипта.

## Конвенции и ловушки реализации

- Сначала добавлять/менять серверный контракт, затем вызывать его адаптером; UI не должен подменять серверный результат локальным успешным состоянием. Сохранять публичные `BookingAPI`, `AdminAPI`, `AccountAPI`, события `pp:change` и `pp:session`.
- Availability cache означает только успешно загруженный серверный снимок. Пустой список при loading/error не равен свободному времени; обновлять через `BookingAPI.ready`, `refreshAvailability` и смотреть `availabilityState`.
- Любую мутацию проводить через серверный owner/admin/CSRF check и Store transaction. Не делать сетевой вызов провайдера под write-lock; после него повторно проверять, что booking и операция всё ещё совместимы.
- Денежные суммы в API отображаются в рублях, внутри сравнений и агрегации использовать точные копейки/Decimal. События оплаты/возврата учитываются по времени фактического подтверждения, в часовом поясе Europe/Moscow.
- URL/host allowlist строится в `create_server`; `PP_PUBLIC_ORIGIN` должен быть HTTPS origin без path. `.env.example` только документирует имена переменных: процесс сам `.env` не загружает.
- При изменении state добавить default для новых коллекций и не удалять существующие ключи. Изменение схемы проверять на миграционном пути; на Windows сначала остановить предыдущий процесс сервера, иначе старый процесс может отвечать со старой схемой.
- Не трактовать настройки ЮKassa как факт готовности без валидной конфигурации и ответа merchant API. Не трактовать наличие generic access-коннектора как совместимость оборудования или реальный unlock.
