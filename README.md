# Ping Point

Выбранный вариант сайта — `1-neon`. Нужен Python 3.11 или новее. Для запуска сайта установите закреплённые runtime-зависимости: `python -m pip install -r requirements.txt`. Полный набор для разработки и проверок устанавливается отдельно, как описано в разделе «Проверки»; сборки фронтенда нет.

## Запуск общего бронирования

Из этой папки:

```powershell
python server.py --port 8767
```

Откройте [сайт](http://127.0.0.1:8767/1-neon/index.html). Этот сервер одновременно отдаёт страницы и общее API бронирования. Обычный `python -m http.server` годится только для статических страниц: общее бронирование на нём недоступно.

Для проверки сценария оплаты без движения денег:

```powershell
python server.py --port 8767 --demo-payments
```

Только этот явный флаг включает имитацию оплаты и тестовые отметки администратора. Карта `5555 5555 5555 4444` проходит в тестовом режиме; другие номера отклоняются. СБП также имитируется. Настоящие реквизиты вводить не нужно. Код двери не генерируется. Без флага подтверждение платежа с клиента невозможно: сервис сообщает, что провайдер оплаты ещё не подключён.

Данные сохраняются в `.data/bookings.sqlite3` и переживают перезапуск. Каталог закрыт для HTTP и исключён из Git. Для отдельной тестовой базы используйте `--database C:\путь\к\отдельной.sqlite3`; резервную копию базы делайте после остановки сервера. `--bind` по умолчанию равен `127.0.0.1`, сайт доступен только на этом компьютере.

## Доступ и сохранность

Все посетители одного сервера видят одну занятость. Новая бронь удерживает время 15 минут; неоплаченная бронь истекает, отменённая освобождает интервал. SQLite-транзакция предотвращает двойное бронирование при одновременном запросе. Рабочее время и тарифы проверяются сервером, время комнаты считается в Москве (UTC+3). Публичная сетка содержит только интервалы, статус и тарифы, без телефонов, имён и кодов. Если ЮKassa подтвердит оплату после истечения удержания, сервер повторно проверит время: конфликт даст `payment_review`, запись поступления и закрытый доступ, а не пересекающуюся бронь.

Гостевая бронь привязана к случайной `HttpOnly; SameSite=Strict` cookie серверной сессии. Номер телефона, известный ID брони или флаг администратора в localStorage доступа не дают. Новые аккаунты и пароли хранятся на сервере; при регистрации/входе присваиваются только гостевые брони текущей cookie. После входа они доступны на другом устройстве. Телефон служит неподтверждённым логином; восстановления по СМС нет. Дополнительный WebAuthn вход использует ключ устройства: отпечаток, лицо или PIN выбирает устройство, биометрия серверу не передаётся. Старые локальные профили и объявления не импортируются по телефону.

Существующие локальные брони и профили сохраняются в браузере: сервер их не импортирует и не удаляет. Старые демонстрационные брони не занимают общую сетку. После сбоя API сайт не подменяет занятость локальными данными и не сообщает об успешной брони.

## Администратор

Перед запуском задайте `PP_ADMIN_LOGIN` и `PP_ADMIN_PASSWORD` в окружении процесса, затем откройте [админку](http://127.0.0.1:8767/1-neon/admin.html). Без обеих переменных вход закрыт. Старый демонстрационный пароль не используется. Не сохраняйте действующий пароль в исходниках, командах общего доступа или Git.

Брони, блокировки, настройки цен и промокоды админки используют серверную сессию и SQLite. Просмотр и модерация старых локальных объявлений/профилей остаются локальными, но адаптер сначала проверяет доступ к серверной админке. Сброс демонстрационных данных отключён, чтобы не затронуть сохранённые данные.

## ЮKassa: подготовленная интеграция

Сейчас реальный магазин, домен и схема чеков ещё не сообщены: без конфигурации интеграция показывает «не подключена». Никаких действующих ключей в репозитории нет. `.env.example` содержит только имена; сервер читает окружение процесса и не загружает `.env` автоматически.

Для подключения нужны `PP_YOOKASSA_SHOP_ID`, `PP_YOOKASSA_SECRET_KEY`, `PP_YOOKASSA_MODE=test|live`, `PP_PUBLIC_ORIGIN` (канонический HTTPS origin без пути) и подтверждённая продавцом схема фискализации. `PP_RECEIPT_MODE=external` требует `PP_RECEIPT_EXTERNAL_CONFIRMED=true` и реально настроенных внешних чеков; это не способ обойти чеки. Для чеков через ЮKassa выберите `PP_RECEIPT_MODE=provider` и задайте свои `PP_RECEIPT_TAX_SYSTEM_CODE`, `PP_RECEIPT_VAT_CODE`, `PP_RECEIPT_PAYMENT_MODE`, `PP_RECEIPT_PAYMENT_SUBJECT`. Значения определяет продавец и его налоговая схема; сайт их не угадывает. Контакт чека — телефон брони. Корректность фискальной схемы/возвратных чеков проверяется с продавцом до live-запуска.

В кабинете магазина настройте уведомления `payment.succeeded`, `payment.canceled`, `refund.succeeded` на `https://<домен>/api/yookassa/webhook`, порт443/8443 по требованиям ЮKassa. Уведомление не является подтверждением: сервер читает объект merchant API и проверяет ID, внутреннюю связь, сумму RUB, paid и test. Redirect в кабинет также ничего не подтверждает; игрок может повторить сверку. Ключи никогда не отправляются в браузер; реквизиты карты вводятся только на странице ЮKassa.

Перед внешним HTTP сервер сохраняет попытку, точные параметры и idempotency key в SQLite. Повтор/обрыв/перезапуск использует ту же попытку; неподтверждённый исход старше24ч требует ручной сверки, новый ключ автоматически не создаётся. HTTP выполняется вне write-транзакции. Поступление, пришедшее раньше create-response, может восстановиться через проверенный webhook с metadata. Возврат имеет отдельную persisted операцию: pending не считается возвращёнными деньгами, только подтверждённый success учитывается в статистике. Неизвестный исход возврата сверяется через обновление платежа; спустя24ч без provider ID требуется ручная сверка. Изменение цены реальной оплаченной брони при переносе отклоняется до отдельного расчёта; перенос за ту же цену работает.

Поступления считаются по `paidAt`, возвраты — по подтверждённым событиям, в Москве. Это суммы до комиссии, не прибыль. Тестовые платежи показываются отдельно. Test-магазин и `--demo-payments` никогда не дают реального прохода. Для локальной проверки не задавайте live-ключи и не включайте demo на публичном хостинге.

Официальные контракты: [процесс оплаты](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process), [идемпотентность](https://yookassa.ru/developers/using-api/interaction-format), [уведомления](https://yookassa.ru/developers/using-api/webhooks), [возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds), [чеки](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/payments).

## QR и СКУД

После подтверждённой реальной оплаты владелец получает один серверный QR через `GET /api/bookings/{id}/access`. Он одинаков для гостевой брони и кабинета, содержит случайный непрозрачный токен без персональных данных и стандартный SVG с quiet zone. В обычных списках, аналитике и журнале токена нет. Доступ строго `начало <= серверное время < конец` по Москве: повторный вход разрешён, до начала и ровно в конце — запрещён. Отмена, запрос возврата, неявка и перенос отзывают старый QR; перенос выдаёт новый. Регистрация без оплаты, demo и test не дают пропуска.

Модель СКУД/считывателя пока неизвестна. Подготовлен только generic online-коннектор, совместимость и физическое количество проходящих не обещаются. `PP_SKUD_DEVICE_TOKEN` — отдельный случайный секрет устройства, `PP_SKUD_DOOR_ID` — согласованный ID двери. Считыватель передаёт `POST /api/access/verify` с `Authorization: Bearer <device token>` и JSON `{payload,doorId,requestId?}`. Ответ `{allowed,reason,bookingId?,validUntil?}` — решение, а не команда открытия. Секрет нельзя размещать в общедоступном браузерном JS. Доступ без правильных bearer и doorId запрещён; отсутствие сети, HTTPошибка или неизвестный ответ должны запрещать проход на стороне адаптера. Offline-режима нет.

Администратор видит готовность интеграций и журнал решений без QR. `POST /api/admin/access/simulate` требует admin+CSRF и всегда возвращает `simulation:true`; команды двери не отправляет. Настройка этих переменных не подтверждает совместимость оборудования: после ответа клиента нужны вендорный адаптер, проверка сети/считывания, fail-closed поведения и полевое испытание. Реальные финансовые операции, публикация и открытие двери в этой локальной сборке не выполнялись.

## Проверки

Для полной проверки нужны Python и Node.js. Из корня проекта установите runtime- и dev-зависимости одной командой:

```powershell
python -m pip install -r requirements-dev.txt
node tests/check.mjs
```

`requirements-dev.txt` включает `requirements.txt` и закреплённые OpenCV, NumPy и Pillow для независимой проверки QR. Эти три пакета не нужны для запуска сайта. Установку и проверки выполняйте одним Python из выбранного окружения: `tests/check.mjs` запускает команду `python` из `PATH`.

Чтобы проверить в отдельном чистом окружении на Windows PowerShell без активации скриптом:

```powershell
python -m venv .venv
$env:PATH = (Resolve-Path .venv\Scripts).Path + [IO.Path]::PathSeparator + $env:PATH
python -m pip install -r requirements-dev.txt
node tests/check.mjs
```

Единая команда `node tests/check.mjs` включает Python- и Node-тесты и проверку синтаксиса. Отдельные команды:

```powershell
python -m unittest discover -s tests -p "test_*.py"
node tests/check.mjs
node --test tests/*.test.mjs
```

Python-тесты поднимают серверы на случайном loopback-порту и временной базе. Они проверяют независимые сессии, гонку за один интервал, конфликты переноса, истечение, отмену, приватность, CSRF, повтор платежа, админку и сохранение после перезапуска. Node-тесты проверяют адаптер и регрессии локальных API без изменения данных рабочего браузера.

`tests/test_payments.py` запускает отдельный настоящий loopback HTTP mock ЮKassa: никаких реальных финансовых запросов. Factory `create_server(..., payment_provider=...)` позволяет программно внедрить такой адаптер, без debug HTTPмаршрутов. `tests/test_access.py` растеризует именно SVG, возвращённый API, и независимо декодирует OpenCV, затем проверяет интервалы, повторный вход и отзыв. Его зависимости устанавливаются через `requirements-dev.txt`. Пример отдельной проверки: `python -m unittest discover -s tests -p test_access.py`.

Порядок подключения скриптов: `community.js`, `shared-booking.js`, затем `booking.js`. Публичные методы `BookingAPI` и booking-методы `AdminAPI` сохранены. Дополнительно доступны `BookingAPI.ready`, `refreshAvailability(date, excludeId?)`, `refreshAllAvailability(dates, excludeId?)`, `availabilityState(date, excludeId?)` и `demoPayments`. Синхронный `availabilitySync` возвращает только загруженный серверный кеш; до загрузки и при ошибке — пустой массив. `availabilityState` сообщает `{status:'loading'|'ready'|'error', error?:string}`. При неизменном ответе повторный запрос не генерирует `pp:change`.
