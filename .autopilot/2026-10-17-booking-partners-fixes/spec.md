# Спецификация: Ping Point — исправление бронирования и объявлений

## Задача
Посетители видят выдуманную занятость и неочевидные цены; выбор времени и длинная форма мешают опубликовать объявление.

## Решение
- R01: раздел «Время» показывает реальные свободные получасовые окна комнаты; отсутствие брони означает свободное окно. Демонстрационные брони исключаются без потери пользовательских данных. Прошедшее время и час до начала отдельно обозначены недоступными.
- R02: новая бронь удерживает время, оплаченная занимает его, отменённая или истёкшая освобождает. Повторная бронь пересекающегося времени отклоняется. Обновление сетки после брони, отмены, возврата на вкладку. Общий источник — сервер этого сайта, подтверждён пользователем.
- R03: все сравнения с фитнесом, сравнительные бары, сноски и комментарии удалены; вместо них прозрачный расчёт аренды, дополнительных ракеток, общей суммы и доли каждого игрока. Подсказка позвать друзей не повторяет бессмысленно текущий состав из четырёх.
- R04: при выбранных периодах точное начало ограничено их диапазонами, шаг 30 минут; утро 10:00–12:30, день 13:00–16:30, вечер 17:00–19:30 при минимуме игры 1 час. Без периодов — весь рабочий диапазон. Несовместимое старое значение очищается с понятной подсказкой. API также проверяет диапазон, конечность и шаг; предложения времени в откликах соблюдают точное время.
- R05: путь «Разместить объявление» через вход и необходимые документы продолжается автоматически. Форма разбита на короткие шаги с доступными действиями «Далее», «Назад», «Опубликовать», понятными ошибками у полей и сохранением введённых данных при возврате или ошибке. Не публиковать дважды при двойном клике, ошибку API показывать в текущем шаге. После успеха объявление видно в кабинете и ленте. Условия согласий сохраняются, не обходятся и не включаются автоматически.
- R06: убрать белые системные рельсы прокрутки в модальных формах; сохранить колесо, касание и клавиатуру, один вертикальный контейнер, доступность низа, заголовка и действий. Проверка 375 px, 1440 px, небольшая высота окна.
- R07: цены показывают оплату за комнату в час, 400/500 в текущей сетке; явно «при 4 игроках» и «за час»: 400 ÷ 4 = 100 ₽, 500 ÷ 4 = 125 ₽. Выходные по той же сетке, убрать неясную карточку «0 ₽ наценки». Интервал через 13:00 считается по частям с ясным примером 12:00–14:00 = 400 + 500 = 900 ₽ за стол.

## Решения по реализации
Сохранить текущие HTML/CSS/JS без сборщика. CommunityAPI/BookingAPI/AdminAPI — существующие границы, добавляется сервер Python 3.11 stdlib + SQLite и адаптер shared-booking.js поверх текущих API. Два таска: общий источник, затем интерфейс. Без нового поставщика услуг и расходов.
Проверки: node tests/check.mjs (проверка синтаксиса страниц и meaningful регрессии API), отдельно node --test tests/*.test.mjs. Браузерная приёмка через CUA.

## Вне рамок
Публикация на хостинг, настоящая оплата и выдача дверного кода, подключение СМС не запрошены. Не менять цены и правила бизнеса.

## Открытые места
Общий источник подтверждён. Настоящая оплата, СМС-авторизация и публикация на хостинг остаются отдельными интеграциями; локальная проверка использует явно включённую тестовую оплату.

## Общий источник бронирования
Python HTTP-сервер обслуживает статический сайт и same-origin API, SQLite хранит настоящие созданные брони без генератора фиктивных записей. Сервер — источник истины: атомарная транзакция проверяет пересечение и создаёт 15-минутное удержание; отмена/истечение освобождают время. Пользовательский браузер имеет непредсказуемую сессию/ключ владения; API не раскрывает посторонним имя, телефон, сумму или код входа. Публичная занятость содержит только интервалы и состояния. Дата и время считаются в Europe/Moscow (или фиксированный UTC+3), независимо от timezone сервера. Перезапуск не теряет базу.
Адаптер обновляет сетку асинхронно при входе в раздел «Время», смене дня, открытии брони, возвращении вкладки и периодически; до ответа нет ложного «свободно», при ошибке ясно показано «Не удалось загрузить» и повтор. После создания/оплаты/отмены/переноса обновляет кеш и события. Никакого автоматического fallback к локальной занятости при недоступности сервера.
Все методы, способные менять занятость, используют сервер: включая клиентский перенос и операции бронирований/блокировок админки. Серверная админка не доверяет флагу localStorage и старому демонстрационному паролю; доступ конфигурируется переменными окружения. Публичный API не отдаёт приватные данные. Сервер сам валидирует время, длительность, цены и статус, не доверяет значениям клиента.
Существующие реальные локальные записи сохраняются в браузере; фиктивные demo записи не влияют на сервер. Не импортировать реальные записи без отдельного действия пользователя и не удалять их. Профили и объявления пока сохраняют текущую модель браузера: их серверный перенос не запрошен.
Тестовая оплата — только явно включённый локальный режим, без реального движения денег; вне него не подтверждать оплату со слов клиента. Документация содержит запуск, хранение базы и пределы готовности к публикации.
Регрессии: два независимых владельца видят одну занятость, гонка за один интервал даёт один успех, чужую бронь нельзя прочитать или отменить, истёкшее удержание и отмена освобождают, перенос проверяет пересечения, SQLite переживает рестарт.

## Уточнение существующей ручной брони (итоговая проверка)
Старая AdminAPI.createBooking поддерживала ручную сумму и заметку, а новый сервер молча игнорировал эти поля. Сохранить существующую административную возможность, проверяя сумму и ограничивая заметку на сервере; обычный клиент задавать цену не может. Промокод ручной брони проверяется сервером до показа финальной суммы, preview и сохранение согласованы. Это восстановление прежнего интерфейса, не новый тариф или бизнес-правило. Закрытие индикатора загрузки отменяет последующее открытие формы.
