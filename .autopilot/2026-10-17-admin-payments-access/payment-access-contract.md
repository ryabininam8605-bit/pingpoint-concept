# Контракт 02 для UI и приёмки

- `GET /api/session.capabilities.payments`: `disabled|demo|test|live`; `access`: `unconfigured|online`. Оплата без конфигурации возвращает503 `PAYMENT_DISABLED`. Demo — явная прежняя имитация, никогда не дверь. Test ЮKassa — redirect, но без реального пропуска.
- `POST /api/bookings/{id}/payments {}` → `{id,bookingId,amount,method,status,createdAt,paidAt,test,provider:'yookassa',providerId?,confirmationUrl?,reviewReason?}`. Сумма только серверная. `confirmationUrl` — redirect на платёжную страницу; сайт не принимает PAN/CVV в test/live. Повтор возвращает одну durable попытку. Body method игнорируется: способ выбирается на стороне ЮKassa.
- `POST /api/payments/{id}/refresh {}` → `{payment,booking}`; redirect сам оплату не подтверждает.503 `PROVIDER_PENDING` означает неизвестный исход, повторяется сверка/та же попытка.409 `PAYMENT_REVIEW` означает ключ старше24ч, автоматический новый платёж запрещён.409 `PROVIDER_MISMATCH` — проверка администратора.
- Durable операции привязаны к `{shopId,mode,endpoint}` без secret key. Перед любым provider IO и применением ответа сверяется `providerContext`; смена магазина/режима/endpoint или старая операция без сохранённого контекста даёт409 `PAYMENT_CONFIG_CHANGED` без HTTP. Требуется восстановить исходную конфигурацию и сверить; тихого переназначения операции другому магазину нет. Программный mock adapter должен сохранять стабильные `shop_id` и `base_url`.
- Статусы брони добавлены `payment_review` (деньги получены, слот недоступен; вход закрыт), `refund_pending` (возврат в обработке; вход закрыт). Статус платежа `requires_review` с `paidAt` учитывается в поступлениях, но не даёт доступа. `refund_partial` сохраняется как прежний статус поздней отмены/частичного возврата.
- Реальная отмена вызывает `POST /refunds` ЮKassa, только подтверждённый success меняет refunded/refundedAt. Неопределённый исход остаётся pending и сверяется через `/payments/{id}/refresh`; администратор использует прежние `/api/admin/bookings/{id}/partial-refund {amount}` и `/refund-fault {}`. Возврат отозвал доступ уже при запросе. Pending возврат не является возвращёнными деньгами.
- `refundOperations.succeededAt` — серверное время первого подтверждённого перехода в succeeded, а не provider `created_at` запроса; повтор уведомления дату не меняет. Если подтверждение получено после долгого pending, возврат входит в дату подтверждения.
- Перенос с той же ценой создаёт новый QR, старый отозван; перенос реальной оплаченной брони с разницей цены409 `SETTLEMENT_REQUIRED`, без тестового движения денег.
- `GET /api/bookings/{id}/access` owner/admin only → `{status:'unavailable'|'scheduled'|'active'|'expired'|'revoked',reason,test:false,validFrom?,validTo?,qrPayload?,qrSvg?}`. QR только для scheduled/active **реальной** оплаченной брони. `qrSvg` — готовый стандартный SVG qrcode8.2, quiet zone4; `qrPayload` единый непрозрачный `pp1_` +32 randombytes base64url. Нельзя создавать QR из booking.id/code; нельзя показывать такой fallback. Token не в обычных booking/list/admin/analytics.
- Reasons reader: `active`, `scheduled`, `expired`, `revoked`, `payment_invalid`, `refund_pending`. Получение QR ещё не обещает подключённую дверь: UI обязан рядом учитывать `capabilities.access` и сообщать «СКУД не подключена» при unconfigured.
- Reader `POST /api/access/verify` Bearer `PP_SKUD_DEVICE_TOKEN`, `{payload,doorId,requestId?}` → `{allowed,reason,bookingId?,validUntil?}`; неверное устройство/дверь403. No browser CSRF. Строго `[validFrom,validTo)` по серверу, многократно. Нет маршрута unlock. При сетевой/HTTPошибке контроллер обязан запрещать проход. Конкретная модель СКУД ещё неизвестна.
- Admin simulator `POST /api/admin/access/simulate {payload,doorId}` требует admin+CSRF; всегда `simulation:true`, события помечены reason=`simulation:...`. Может показать решение, но никогда не посылает команду двери.
- `/api/admin/integrations` возвращает readiness payment/access/passkeys безсекретов, `missing` содержит толькоимена env. `/api/admin/access-events?limit=50` возвращает только `{at,bookingId?,doorId,result:'allow'|'deny',reason}`, безpayload. `/api/admin/payments?mode=live|test` теперь фильтрует деньги; безmode сохраняетсяlegacyконтракт. `/api/admin/bookings/{id}` добавляет `refunds:[{id,paymentId,amount,status,createdAt,succeededAt?,providerId?}]`.

## Конфигурация
В окружении процесса: `PP_YOOKASSA_SHOP_ID`, `PP_YOOKASSA_SECRET_KEY`, `PP_YOOKASSA_MODE=test|live`, `PP_PUBLIC_ORIGIN=https://...`, `PP_RECEIPT_MODE=external|provider`. External требует осмысленного подтверждения продавца `PP_RECEIPT_EXTERNAL_CONFIRMED=true`. Provider требует `PP_RECEIPT_TAX_SYSTEM_CODE`, `PP_RECEIPT_VAT_CODE`, `PP_RECEIPT_PAYMENT_MODE`, `PP_RECEIPT_PAYMENT_SUBJECT`; значения задаёт продавец, не генератор. Чек использует телефон самой брони. Безсхемы фискализации режимdisabled. `.env.example` пустой, автоматика его нечитает.

`PP_SKUD_DEVICE_TOKEN`, `PP_SKUD_DOOR_ID` настраивают generic onlineauthorization; это неутверждение о совместимости с отсутствующей моделью устройства. Нетfallback defaulttoken.

## Безопасные acceptancefixtures
`create_server(..., payment_provider=provider)` принимает только программный adapter, никаких debug HTTP routes. Adapter имеет `mode`, `origin`, `receipt(booking,amount)`, `readiness()->{configured,mode,missing,message}`, `request(method,path,data=None,key=None)`. В tests/test_payments.py — `MockProvider(url,test=False)` с настоящим отдельным loopbackHTTPserver. Только temporaryDB. Нетобращений к реальнойЮKassa/СКУД.
РеальныйSVGизAPI растеризован изXMLpath и независимо прочитан OpenCV `QRCodeDetector`, токен совпал полностью: `python -m unittest discover -s tests -p test_access.py`. Используются имеющиеся dev `cv2`, `numpy`, `PIL`; runtime остаётся qrcode8.2.
