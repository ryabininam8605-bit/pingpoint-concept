# Exploration: admin, identity, payments, scheduled entry

Read-only inspection of HEAD `bab149a`, 2026-10-17. No product code changed. Provider, hardware, hosting and authentication choices are pending user clarification; this file does not establish those facts.

## Existing boundaries

- `server.py` is one Python stdlib HTTP service. `Store` stores one JSON state document in SQLite `state(id,data)`; only `sessions(token,csrf,admin,expires)` is normalized. A transaction takes `BEGIN IMMEDIATE`, loads state, expires holds, calls an operation, and writes state. Initialization only inserts the initial state if missing: new collections require additive/default migration for existing databases.
- State currently has `settings`, `bookings`, `payments`, `blocks`, `promos`, `seq`, `consents`. There are no server users, registration events, access grants, access events, webhook events, provider IDs or durable external-operation outbox.
- A visitor gets a random 180-day HttpOnly SameSite=Strict cookie. Only the SHA-256 cookie digest is stored; it is also `booking.owner`. Session CSRF is required on every POST. Admin authority is a session column, gained with environment login/password. Public file serving is restricted to `/1-neon/` and allowed extensions, protecting SQLite and environment files.
- `create_server(host='127.0.0.1',port=8767,db_path=None,demo_payments=False,admin_login=None,admin_password=None)` is used by tests. Preserve compatibility of this factory. Host allowlist currently permits only bind host, localhost, 127.0.0.1 plus bound port: real public host/reverse proxy requires explicit config. Cookie currently lacks Secure; public HTTPS deployment needs a trusted configured origin/secure-cookie mode rather than trusting forwarded headers from everyone.

## Identity is browser-local

- `CommunityAPI` in `1-neon/community.js` owns local users, profiles, ads, responses, documents and consent history. Its `requestCode(phone)` never sends SMS, returns `{sent:true,exists,demoCode:'1234'}`. `register({phone,code,name,ageGroup,guardian,consents,context})`, `login({phone,code})`, `logout()`, `me()`, `meSync()` all use localStorage. Server does not trust them.
- `meView` shape: public profile plus `phone`, `phoneRaw`, `tg`, `showPhone`, `createdAt`, `completeness`, `ageGroup`, `guardian`, `deletion`, `docsOk`, `publicOk`, `publicCond`, `outdated`. Cabinet and booking UI read `meSync()` synchronously, so a server adapter needs readiness/cached identity semantics and must prevent stale logged-in UI during bootstrap or logout.
- Registration requires `consent_pd`, `community_rules`, `policy`, explicit adult/minor selection and guardian data for minors. Server booking stores canonical document hashes/revisions for three booking consents; registration/document actions remain local.
- Existing CommunityAPI methods that affect profile rights: `updateProfile`, `docs`, `outdatedDocsSync`, `acceptDocs`, `setPublicConditions`, `revokeConsent`, `restoreProfile`, `deleteProfile`, `exportMyData`. A minimal auth-only override risks breaking local ads, because these methods use private lexical `currentUser(db)` reading local session IDs. Need a deliberate compatibility bridge or server migration of their authority, not just override `me()`.
- Existing local profiles cannot be trusted as authenticated server identities or imported on phone alone. Preserve old local data, do not count seeded/demo users in actual admin stats. Verified sign-in can explicitly claim only the current cookie's guest bookings safely; claiming historical bookings by unverified client phone creates account takeover. User-auth provider and registration migration must be specified.

## Existing booking and money lifecycle

- Public booking routes: GET `/api/session`; GET `/api/availability?date=&excludeId=`; POST `/api/promos/apply`; POST `/api/bookings`; GET `/api/bookings/mine`; GET `/api/bookings/{id}`; POST suffixes `/payments`, `/cancel`, `/reschedule`, `/reschedule-quote`; POST `/api/payments/{id}/confirm`.
- `private_booking` allows exact cookie owner or server admin. `listMyBookings` also filters exact cookie owner; `userId` is always null on server-created bookings. Registered users currently gain no cross-device booking authority.
- Booking creation validates schedule/conflicts and price on server, preserves quote/promocode terms, holds slot for 15 minutes. Occupancy includes pending/paid/noshow. Expiry cancels pending payments. Money values are rubles, potentially represented as floats (half-hour increments); provider boundary should convert exactly to integer kopecks/decimal strings without trusting browser total.
- All online payment and cash/terminal admin marks currently require `--demo-payments`. `payment` creates `{id,bookingId,amount,method,status,createdAt,paidAt,cardMask,refundedAt,test:true}`. `/confirm` accepts only test card/SBP and directly marks paid. There is no real card handling, HTTP provider request, signature check, reconciliation, or receipt construction.
- Demo confirmation intentionally creates `code:null,test:true`. Preserve the impossibility of issuing an actual entrance pass from test payment. New production flow must never accept client success redirect/confirm as proof of payment.
- `cancel_booking`, `refund_amount`, admin partial/fault refund and reschedule charge differences all mutate simulated accounting immediately. Real integration must cover these call sites, not just initial create-payment. Existing reschedule accepts one user move until 3h before start; if amount differs, it currently calls demo payment/refund directly. Safe real support can use explicit pending adjustments or reject unsupported money-changing transfer rather than report imaginary settlement.
- External provider HTTP must not happen while holding the SQLite state transaction lock: HTTP timeout/retry/webhook race would block every booking and access check. Durable idempotency keys + prepared operation + external call + atomic application/reconciliation are needed; late successes after expired hold require explicit policy and no overlapping paid entry grants.

## Admin UI and data correctness

- `admin.html` already has login and sections: dashboard, bookings, payments, clients, community, settings, consents. Current page is an extension target, not a new unrelated app.
- Shared adapter overrides booking/admin APIs in `1-neon/shared-booking.js`, loaded after `community.js` and before `booking.js`. It bootstraps `/api/session`, wraps CSRF, preserves `pp:change`, manages server availability cache. Existing remaining local admin methods first check server `/api/admin/auth`, but their data is still local browser data.
- `AdminAPI.dashboard()`, `listPayments(filters)`, `listClients(q)`, `getClient(phone)` are already server-backed. `dashboard` currently returns booking-date revenue `today/week/month`, booking counts, load and heatmap, repeat share, todayList etc. Do not silently reuse booking-date revenue as cash received: user expects payments and cash stats. Specify payment paidAt/refund event date, Moscow grouping, test segregation, gross/refunds/net, zero-filled periods.
- `listPayments` filters by payment createdAt (not paidAt); sums succeeded/refunded/partially_refunded; currently all are test. `clients` groups booking phone, excludes registration-only users, `hasCabinet:false`, detail `profile:null`. `consentStats`, consent lists and community moderation remain local. Real registration list must query persisted real users including those without any booking.
- Existing dashboard has accessible SVG occupancy bars and a heatmap. Revenue and registration trends can use similar lightweight SVG plus labeled values/table fallback. Data must include interval, unit, axis labels and empty states; avoid mixing future booking amounts, cash and refunded transactions.

## QR and physical entry

- CRITICAL: `PPUI.qrSVG` / `community.js:2069` is a seeded random matrix with finder patterns. It is decorative, not a QR encoder. Replace for production with a genuine standards encoder and independently decode generated QR in verification.
- `booking.js` success UI currently builds hypothetical payload `b.id+'-'+b.code`; `cabinet.html` builds `b.code||b.id`. Those differ and neither is an actual reader protocol. Define exactly one server-issued QR payload and render the same value everywhere. Keep pass secrets out of analytics, request logs, ordinary lists and query strings.
- No SKUD vendor/model/API, door identifier, reader ability, network topology or physical adapter exists. Do not invent one. A reader capable of online authenticated authorization can consume an opaque random token and receive a server time decision; offline controller requires vendor-specific scheduled credential provisioning and revocation. A website QR screen alone cannot actuate a lock.
- Access must re-check confirmed non-test payment, booking status and current schedule at authoritative server/controller time; expiry/start boundary tests, cancel/refund/no-show/transfer revocation, duplicate deliveries, no replay beyond agreed policy and loss of connection all need explicit handling. Whether one pass admits a company repeatedly or individual one-time entries is a business rule pending user answer.

## Suggested ownership and waves

1. Foundation ticket alone: additive server identity/session/storage migration and stable shared contracts; preserve factory and booking ownership tests. Own `server.py` initially, a new identity module, identity tests. Freeze integration seams before parallel work.
2. Payment module ticket: new provider adapter/service modules + tests. No direct concurrent `server.py` edit; orchestrator can assign later integration ticket to foundation executor. Requires documented provider contract and fiscal/config choice. Verify provider mocks, forged/duplicate/out-of-order notification, idempotent create/refund, reconciliation, late settlement.
3. Access module ticket: new access domain/adapter modules + tests plus genuine QR library/helper with isolated path. Requires real hardware docs or explicit bounded generic connector contract; no hardware actuation in tests.
4. UI identity/booking ticket: `community.js`, `shared-booking.js`, `booking.js`, `cabinet.html`, identity/booking JS tests. Own these together due existing tight lexical coupling. Wait for contracts; do not overlap adapter files with admin frontend ticket.
5. Admin ticket: `admin.html`, dedicated new admin API/statistics frontend module if needed, admin UI tests. Backend stats should be a named standalone module owned here with sequential integration into server by designated owner, or assigned to foundation owner to avoid overlapping server changes.
6. Final integration/deployment docs ticket: factory config, webhook/controller routes, `.env.example`, README, integration tests; one owner edits server glue after dependent modules land. Must not leave provider-disabled boundary mislabeled as live integration.
